## User Story

As a **Seerflow maintainer and first-time Seerflow user**
I want **the guide to stay accurate as the code evolves, to include an auto-generated API reference plus a 15-minute quickstart, and to capture what we learned building EPIC-DOC**

## Description

### Background

EPIC-DOC (S-139 / SEE-142) shipped 13 child stories and ~41 points of content: docs infrastructure, security primer, architecture, entity graph, detection deep dives, correlation, operations guide, visualizations, ops primer, dual-lens integration. The `seerflow-guide` repo is live at `https://seerflow.github.io/seerflow-guide/`.

Three gaps remain before we can treat the guide as "v1.1 shippable":

1. **No drift guard.** When we renamed `graph.*` → `entity_graph.*` config keys (S-139G-F2), docs silently drifted from the code. S-139G-F1 and S-139G-F2 were both reactive fixes. Without a CI gate, the next config/CLI rename will break docs again and we'll find out from a user GitHub issue.
2. **Missing foundational content.** There is no auto-generated API reference, no quickstart tutorial, and no landing page for frontend docs (Sprint 10+). A prospective contributor who lands on the guide today cannot answer "how do I ingest my first log?" in under 15 minutes.
3. **No retrospective.** 41 points of doc work generated hard-won knowledge about what estimation, review, and Linear sync patterns worked. If we don't capture it, the next epic will repeat the same mistakes (e.g., S-139G underestimated param-reference coverage; S-139H needed two follow-ups).

This story is the capstone: it closes the drift feedback loop, fills the biggest content gaps, and captures lessons before context evaporates.

### Scope

**In scope:**
- **(a) Drift guard** — a reusable `check_docs_drift.py` script + GitHub Action in `seerflow-guide` that fails CI when:
  - Config parameter names in `docs/reference/configuration.md` diverge from the pydantic/msgspec schema in `src/seerflow/config.py`
  - CLI flags documented in `docs/reference/cli.md` diverge from `seerflow --help` output
  - Internal markdown links are broken (markdown-link-check, internal-only fail; external warn-only)
- **(b) Content expansion (minimum viable)**
  - Auto-generated API reference via `mkdocstrings[python]` plugin, mounted at `docs/reference/api.md`
  - Quickstart tutorial at `docs/quickstart.md` — Docker compose + sample log dump + expected alert, 15-minute walkthrough
  - Frontend guide **stub** at `docs/frontend/index.md` with "Coming in Sprint 10" + link to S-060
- **(c) EPIC-DOC retrospective** — `docs/retros/epic-doc-2026-04.md` with planned-vs-actual points, time per story pulled from Linear completion dates, top lessons, top action items, links to every child story. Posted as Linear comment on SEE-142, then SEE-142 marked Done.

**Out of scope (deferred to a later story or epic):**
- Video walkthroughs (production cost too high for capstone)
- Full frontend documentation (cannot write docs for code that doesn't exist yet — Sprint 10 deliverable)
- Screenshot regeneration automation (no automated way to re-render entity-graph-explorer screenshots without running the full stack — defer until S-060)
- Drift guards for prose (e.g., "this paragraph mentions a feature we removed") — would require LLM review; out of scope
- i18n / translation pipeline
- Search analytics + feedback widget (separate story if desired)

### User Flow

**Flow 1 — Maintainer merges a config rename:**
1. Dev renames `hst.num_trees` to `hst.trees` in `src/seerflow/config.py`
2. Dev opens PR on `seerflow/seerflow`
3. Dev forgets to update `docs/reference/configuration.md` in `seerflow-guide`
4. CI on the code PR passes (no docs change)
5. Dev opens any subsequent PR on `seerflow-guide` (or scheduled weekly drift-check run)
6. `docs-drift-check` workflow runs, pulls latest `seerflow` config schema, diffs against docs, fails with clear message: "Config key `hst.num_trees` documented but not in schema. Did you mean `hst.trees`?"
7. Dev updates docs, CI passes

**Flow 2 — New user quickstart:**
1. New user lands on `docs.seerflow.dev`
2. Clicks "Quickstart" in nav
3. Runs `docker compose up` from the provided snippet
4. Pipes sample log dump through Seerflow
5. Sees expected anomaly alert in terminal output
6. Reads explanation of which detector fired and why
7. Done in under 15 minutes

**Flow 3 — Team retro consumption:**
1. Sprint planning meeting
2. Scrum master pulls up `docs/retros/epic-doc-2026-04.md`
3. Reviews action items — e.g., "Add param-reference coverage check to story template"
4. Items feed into next sprint plan / CLAUDE.md updates

## Technical Notes

### (a) Drift guard

**Script: `scripts/check_docs_drift.py`**

Minimal structure — 3 checks composed from small functions:

```
check_docs_drift.py
  check_config_drift()    → parse docs/reference/configuration.md code blocks,
                            load seerflow.config.Config schema, diff keys
  check_cli_drift()        → parse docs/reference/cli.md flag list,
                            run `seerflow --help`, diff flags
  check_links()            → invoke markdown-link-check subprocess
  main()                   → run all, collect failures, print report,
                            exit(1) if any fail
```

**Config drift approach:**
- Import the Seerflow `Config` schema directly (the script runs in an env where `seerflow` is pip-installed — the docs repo already has a `dev` extras for building)
- Recursively walk the schema to build a set of fully-qualified keys (e.g., `{"hst.trees", "hst.height", "holtwinters.alpha", …}`)
- Parse `docs/reference/configuration.md` for fenced YAML blocks, load each as a dict, recursively collect keys
- Diff: keys in docs but not in schema = "documented but deleted"; keys in schema but not in docs = "undocumented" (warn-only for now)

**CLI drift approach:**
- Run `subprocess.run(["seerflow", "--help"])`, capture stdout
- Parse flags (regex `^\s+--[\w-]+` or use argparse introspection if Seerflow exposes it)
- Parse `docs/reference/cli.md` for `--flag` mentions in code blocks
- Diff

**Link check:**
- Use `markdown-link-check` (Node package) or Python `pymdownx.linkchecker` equivalent
- Config file: `.markdown-link-check.json` with `ignorePatterns` for localhost and `retryOn429: true`

**GitHub Action:**

```yaml
name: docs-drift
on:
  pull_request:
    paths: ['docs/**', 'scripts/**', 'mkdocs.yml']
  schedule:
    - cron: '0 12 * * 1'  # Mondays 12:00 UTC
jobs:
  drift:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: '3.11' }
      - run: pip install -e .[dev]
      - run: pip install seerflow @ git+https://github.com/seerflow/seerflow@main
      - run: python scripts/check_docs_drift.py
      - if: failure()
        uses: actions/github-script@v7
        with:
          script: |
            // post PR comment with drift report
```

**Edge cases:**
- If `seerflow` package isn't available, script must fail loud with clear install instructions, not silently skip
- Markdown link check must handle anchor links (`#heading`) and cross-page relative links
- Weekly scheduled run must not post PR comments (no PR context); just fail the workflow and rely on notifications

## Brainstorm Notes

### Scope reality check

The story as drafted has three deliverables split across two repos:

1. `seerflow-guide` (separate GitHub repo at `seerflow/seerflow-guide`) — receives the bulk of the work (drift script, GitHub Action, mkdocstrings config, quickstart, frontend stub, retrospective markdown).
2. `seerflow` (this repo) — receives only a couple of cross-reference updates: a link from the sprint plan to the retrospective and an "Epic complete" annotation on `docs/stories/S-139.md`.

Implementing directly in `seerflow-guide` from inside this isolated agent session is out of scope: the agent is rooted at `/home/fflores/PycharmProjects/seerflow`, the PR target is the `seerflow` repo's `dev` branch, and we cannot reliably push to another repo from this session without entangling credentials and review gates.

**Decision:** stage every `seerflow-guide` deliverable as committed artifacts under `documents/seerflow-guide-staging/` in this repo. The PR description lists exactly which files copy to which paths in `seerflow-guide` and what its companion PR there must do. The cross-repo PR itself is a follow-up story (see deferred section). This keeps the work auditable, code-reviewable, and recoverable while not falsely claiming we merged anything in the other repo.

### Per-deliverable refinements

**(a) Drift guard.** The original brief proposed using `markdown-link-check` (Node). Cleaner inside a Python-only docs repo to use `linkchecker` (Python) or simply `requests` + `markdown-it-py` for the internal-link subset — but for v1.1 the priority is the *config* + *CLI* drift checks, since those are where the real failures came from (S-139G-F1/F2). Link-check is bundled but stubbed to internal-anchor-only validation in this pass; full external-link validation is deferred. The script must:

- Import `seerflow.config` via `pip install seerflow @ git+...` so it always tests against the latest published schema.
- Walk every `@dataclass` decorated section by `dataclasses.fields()` recursion (the project uses frozen slotted dataclasses, not pydantic — adjust the brief).
- Diff CLI flags by walking `seerflow.cli.build_parser()` recursively over subparsers, not by parsing `--help` text (more robust, less regex).
- Emit a JSON report alongside the human-readable one so the GitHub Action can paste it into a PR comment without re-parsing.

**(b) Content expansion.** The 4-module API reference (`events`, `config`, `storage`, `detectors`) is right-sized — full coverage of ~40 modules would explode the build. For the quickstart, the safer bet for v1.1 is *not* to depend on `ghcr.io/seerflow/seerflow:latest` being live; instead use `uv tool install seerflow` (PyPI / TestPyPI once published, fall back to `pip install -e .` from the cloned repo) and run against the bundled sample. Document the Docker path as "Alternative" once the image is verified live (deferred to S-180-F1 below).

**(c) Retrospective.** Linear MCP data extraction is straightforward but the retro doc itself is prose authoring with judgement calls (what worked, what didn't). To keep this story tractable, the retro is authored from the public artifacts (story files + PR titles in `git log`) — not from interviewing the team — and explicitly flags "interview-validated retro" as a follow-up if desired.

### Alternatives logged (scope-change-deferred)

- *Move drift guard into `seerflow` repo* (so code PRs fail when docs would drift): better DX, but requires a second PR in this repo. Logged for follow-up — flag `scope-change-deferred`.
- *Generate full API reference for all modules*: doubles build time + surfaces undocumented internals. Defer to a future "API ref polish" story.
- *Video walkthroughs / search analytics*: already out-of-scope in the brief.

### Risks

- The `seerflow-guide` PR depends on `seerflow` being pip-installable from `main` *and* exposing `seerflow.config.SeerflowConfig` import surface — both verified above.
- mkdocstrings strictness on missing docstrings could break the build on first import of `seerflow.detectors`. Mitigate by setting `show_if_no_docstring: true` so missing docstrings render an empty body instead of failing.
- The drift script's CLI-flag walk must skip the `--config` global and `--help`/`--version` builtins to avoid spurious diffs against documentation that omits them. Add an `_IGNORED_FLAGS` set.

### Confirmation

Story content otherwise unchanged. The Implementation Plan below is scoped to **what this isolated session can ship in the `seerflow` repo + stage for the companion PR**. Acceptance criteria for items that physically live in `seerflow-guide` are validated *at the staging layer* (script runs, content authored, dogfood test passes against the local `documents/seerflow-guide-staging/` tree) and re-validated when the companion PR opens.

### Task 3 — Drift script: implement config-drift helpers (5 min)

**File:**
- `documents/seerflow-guide-staging/scripts/check_docs_drift.py` (new)

**Steps:**
1. Define `@dataclass(frozen=True) class ConfigDriftReport` with `extra_in_docs: frozenset[str]`, `missing_in_docs: frozenset[str]`, `ok: bool` property.
2. Implement `collect_schema_keys(cls: type, prefix: str = "") -> frozenset[str]` — recurses `dataclasses.fields()`. For nested dataclass fields, descends with prefix. For leaf fields, emits `prefix + name`.
3. Implement `parse_config_yaml_blocks(markdown: str) -> frozenset[str]` — extracts triple-backtick yaml blocks via regex, parses each via `yaml.safe_load`, recursively collects dotted keys, returns the union.
4. Implement `diff_config_keys(schema_keys, docs_keys) -> ConfigDriftReport`.
5. Run the Task 2 tests — expect GREEN.

**Verify:** `uv run pytest documents/seerflow-guide-staging/tests/test_check_docs_drift.py -k config -v` passes.

### Task 4 — Drift script: red tests for CLI drift (3 min)

**File:**

**Steps:**
