# S-101: Add activity_id and related_hashes fields to SeerflowEvent

**Linear:** [SEE-105](https://linear.app/seerflow/issue/SEE-105) | **Epic:** EPIC-002: Log Parsing | **Priority:** Should Have
**Points:** 1 | **Sprint:** 1 — Foundation | **Dependencies:** S-002

## User Story

As the detection pipeline, I want `activity_id` and `related_hashes` fields on SeerflowEvent so that OCSF taxonomy is complete and IoC hash matching works.

## Background

Architecture audit (2026-03-18) found 2 fields defined in the background doc (`Designing Seerflow's event schema and storage backend.md`) that were omitted from both the architecture doc and the S-002 implementation:

1. **`activity_id: int = 0`** — OCSF field. `type_uid = class_uid × 100 + activity_id`, so having `type_uid` without `activity_id` loses the ability to reconstruct the OCSF tuple. Required for OCSF compliance.

2. **`related_hashes: tuple[str, ...] = ()`** — File/process hashes extracted from log events. Required by S-050 (Bloom filter IoC matching) which checks file hashes against threat intelligence indicators.

A third field (`mitre_data_source: str = ""`) was found but deferred — it can be stored in `attributes` until there's a concrete consumer.

## Acceptance Criteria

- [ ] `activity_id: int = 0` added to SeerflowEvent in OCSF section (after `type_uid`)
- [ ] `related_hashes: tuple[str, ...] = ()` added to entity references section (after `related_hosts`)
- [ ] Architecture doc updated: add both fields to the SeerflowEvent definition (line ~595)
- [ ] Existing tests still pass (no breaking change — both fields have defaults)
- [ ] New test: verify `activity_id` default is 0 and accepts int values
- [ ] New test: verify `related_hashes` default is () and accepts tuple of strings
- [ ] New test: msgpack/JSON roundtrip includes new fields
- [ ] `uv run ruff check . && uv run mypy src/ && uv run pytest` all pass
